## Context

采集审核区通过批量操作创建 `AcquisitionImportBatch`，后台任务随后逐项调用图库导入服务。当前批次没有记录目标图片类型，查重固定查询普通图片，因而无法安全支持图文图片；若只在请求处理时传递临时参数，进程重启后的恢复任务也会丢失类型。图库服务已经具备稳定的普通/图文导入分支，图文分支会设置 `is_rich_text`、创建 `#图文` 系统标签并触发 OCR，因此采集流程应复用该入口。

## Goals / Non-Goals

**Goals:**

- 允许用户将当前选中的采集候选图片整批导入为普通图片或图文图片。
- 让目标类型在异步执行、失败重试、历史查询和进程恢复中保持一致。
- 保持普通图片和图文图片按类型独立去重，并兼容旧客户端。
- 复用图库现有图文处理语义，避免形成第二套 OCR 或标签逻辑。

**Non-Goals:**

- 不支持同一个提交批次内逐张指定不同类型。
- 不允许同一待审核资源先后导入为两种类型；导入成功后仍按现有流程消费临时对象。
- 不改变采集任务把“与图库普通图片完全一致”的候选图提前过滤掉的行为。
- 不新增 OCR 配置或改变图库手工上传流程。

## Decisions

1. 在 `AcquisitionImportBatch` 上增加非空布尔字段 `is_rich_text`，默认值为假。请求创建批次时写入该字段，后台处理、失败重试与恢复均从数据库批次读取。相比把类型保存在内存任务参数中，该方案能保证重启恢复一致；相比逐项存储，批次级字段与本次统一类型的交互语义一致。
2. 扩展现有 `POST /api/acquisition/assets/import` 请求体，而不新建接口。普通和图文导入共享权限、选择、批次、进度及错误处理，新增布尔字段可以保持旧客户端兼容，也避免重复维护一套异步工作流。
3. 精确重复查询增加目标类型条件。图库唯一约束本身允许同一工作区、同一 SHA256 在普通和图文类型各存一份，因此图文批次只能把已有图文图判为重复，普通批次同理。
4. 前端使用紧凑的分段选择控件，在执行导入前选择“普通图片”或“图文图片”，默认普通图片。按钮和失败重试操作显示当前类型，历史批次显示已持久化类型，降低误操作风险。
5. 图文批次调用现有 `PictureService.import_gallery_photo(is_rich_text=True)`，不传手工文字，使现有 OCR、`#图文` 标签及人脸处理策略原样生效。
6. 数据库生命周期迁移为旧表补字段并回填假值，同时同步 SQLAlchemy 模型和 `sql/tables.sql`。这符合项目当前无独立迁移框架、由启动生命周期迁移维护兼容性的方式。

## Risks / Trade-offs

- [用户选错类型后无法直接对同一待审核资源再次导入] → 在导入按钮、确认区域和历史记录中清晰显示类型，保持现有成功后消费资源的语义。
- [旧批次数据库没有类型字段] → 迁移使用非空默认假值，所有旧批次解释为普通图片。
- [同一文件跨类型保存会增加存储] → 这是图库既有且有意保留的类型隔离语义；同一类型内仍严格去重。
- [图文导入增加 OCR 耗时] → 复用现有后台导入和 OCR 状态机制，不阻塞 API 请求。

## Migration Plan

1. 启动时为 `acquisition_import_batches` 增加 `is_rich_text` 字段并将旧数据设为假。
2. 部署兼容新字段的后端，再发布带类型选择的前端。
3. 回滚应用时新增字段可以保留；旧代码会忽略该字段，普通导入行为不受影响。
