## Context

现有采集服务将站点适配器输出的图片 URL 下载到 MinIO，并在图片专用审核区中人工入图库。视频库已有独立的对象存储、探测、封面和转码流程。Telegram 需要使用用户 MTProto session 才能访问已加入的私人频道，因此不能复用 HTTP 适配器。

## Goals / Non-Goals

**Goals:**

- 每个工作区独立绑定一个 Telegram 账号和加密 session。
- 手动采集一个频道中的图片和视频，并按时间、标签、文案筛选。
- 在统一审核区展示来源文案和标签，并批量分流入图库或视频库。

**Non-Goals:**

- 不实现实时监听、定时任务、多账号、自动加频道或非图片视频媒体采集。
- 不自动把 Telegram 标签写入图库或视频库标签体系。

## Decisions

- 使用 Telethon 和 MTProto：Bot API 不适合读取频道完整历史与大媒体；每次手动运行建立临时客户端。
- 新建 `telegram_accounts`，以 `workspace_id` 唯一约束保存加密 api hash 和 session；来源及分类继续复用现有采集结构，频道为分类。
- 新建 Telegram 消息与标签表，而不是把文案塞进图片资产字段；一条消息可对应相册中的多个独立媒体资产。
- 扩展采集资产的 `media_type` 和视频元数据。图片继续走现有分析链，视频使用 FFprobe/首帧预览且不进入图片相似扫描。
- 审核批次增加媒体目标类型与视频关联，批量中按资产类型分别调用图库和视频库的导入逻辑。
- session 使用 Fernet 对称加密；密钥由 `.env` 提供，接口只返回脱敏账号状态。

## Risks / Trade-offs

- [Telegram 限流或断网] → 持久化外部键和运行条目，记录失败项并在后续运行重试。
- [视频文件很大] → 采用临时文件下载、配置最大字节数，并在完成后立即清理。
- [现有审核 UI 仅支持图片] → 保持图片交互不变，为视频增加媒体卡片和批量导入分流。
- [SQLite 迁移] → 通过现有生命周期增量迁移添加字段和表，并同步 `sql/tables.sql`。

## Migration Plan

先添加表、字段、索引和依赖，再发布服务代码和前端。旧采集资产统一标记为 `image`，现有图片批次保持原逻辑。回滚时新数据表可保留，旧代码忽略新字段；不得删除已采集对象。
