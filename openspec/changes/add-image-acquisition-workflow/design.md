## 背景

PictureShow 已具备 SQLite、MinIO、图库 SHA256 去重、人物识别和相似图片能力，但采集工作仍在 `catchPics` 中以站点专用脚本和本地目录完成。下载结果与人工筛选、正式入库及后续增量更新相互脱节，无法稳定追溯某次采集最终成功入库的图片。

本设计把采集建模为独立领域：采集适配器只枚举远端条目，采集服务负责下载和状态，审核服务负责临时图片决策，图库服务继续拥有正式图片及识别结果。第一版仅允许运行内置、经审查的适配器，且所有任务在现有进程内执行并持久化检查点。

## 目标与非目标

**目标：**

- 让用户从网页维护采集站点、站点脚本绑定和分类网页，按分类选择脚本并填写脚本参数后手动启动可恢复的增量采集。
- 在临时 MinIO 工作区完成精确去重、质量提示、相似整理和人工审核，再无重复存储地提升至正式图库。
- 记录成功入库图片与采集运行、来源站点和分类的关系，支持历史筛选和低内存 ZIP 导出。
- 复用现有图库导入、识别、相似度和权限能力，不对采集分类作人物或标签含义推断。

**非目标：**

- 不提供任意 Python/JavaScript 脚本上传、执行或站点自动发现。
- 不实现定时调度、个人审美模型、训练流程或依据采集分类自动标注人物。
- 不保存被人工拒绝或技术无效图片的二进制文件，也不改变正式图库删除语义。

## 设计决策

### 以独立采集领域隔离站点逻辑

新增 `AcquisitionSource`、`AcquisitionScript`、`AcquisitionSourceScript`、`AcquisitionCategory`、`AcquisitionRun`、`AcquisitionSourceItem`、`AcquisitionAsset`、`AcquisitionRunItem`、`AcquisitionImportedPhoto`、相似候选和导出任务等模型。`AcquisitionSource` 只保存网站名称、首页 URL、备注和由绑定关系自动确定的网页格式；`AcquisitionScript` 由代码注册表同步，保存稳定键、严格采用原脚本目录名的显示名称、版本、唯一网页格式和参数结构；`AcquisitionSourceScript` 表示一个站点可绑定多个同网页格式脚本。站点适配器只实现枚举远端 `RemoteItem` 的协议，不接触数据库、MinIO 或 HTTP API；服务层负责持久化和下载。

分类网页只保存所属站点、自定义名称、真实 URL、备注和启用状态。分类名称纯粹用于界面辨识，不能参与 URL 拼接、路径推断或脚本分支。启动运行时必须从该站点已绑定的脚本中选择一个，服务端按脚本参数结构校验输入，并把脚本键、版本、分类 URL 与参数快照写入运行记录。

选择此边界是为了让站点信息、可执行脚本和实际待爬网页各自独立，同时避免把站点代码散落到路由或图库服务。新增脚本采用代码评审方式增加独立适配器模块及声明式元数据，注册后前端自动显示，不提供上传或执行任意脚本能力。

### 临时工作区先审核，再提升到图库

所有下载文件先写入 `workspaces/{workspace_id}/acquisition/assets/{asset_id}/...`。下载后计算 SHA256：同一采集工作区只保留一份资产，但每个运行条目保留来源 URL 和状态。确认导入时，服务先使用 MinIO 服务端复制到正式图库对象键，创建图库记录并写入来源关系，确认成功后删除临时对象。

该方案避免已确认图片在 MinIO 中长期双存。替代方案是直接写入正式图库后“隐藏”，会使审核阶段干扰图库、删除语义和既有相似整理，因此不采用。

下载成功后先按工作区和 SHA256 查询正式图库；命中时仅保留来源文本状态并删除临时二进制，不进入待审核、成功入库溯源或导出。由于图库可能在采集完成后发生变化，正式提升前必须再次执行相同检查。

人工入库使用 `AcquisitionImportBatch` 和 `AcquisitionImportBatchItem` 持久化一次提交及全部图片。批次创建与资产切换为排队状态在同一数据库事务中完成；逐张提升使用独立事务和检查点，一张失败不会阻断后续图片。批次项记录处理意图、结果、图库图片和错误，服务重启时据此补齐已经创建图库记录但尚未写入溯源的图片，未生成图库记录的图片进入可重试失败状态并保留临时文件。

### 以来源条目状态实现可控增量

来源条目使用适配器提供的稳定外部键，并在分类与脚本范围内唯一化。默认增量采集跳过已 `imported`、`rejected`、`gallery_duplicate` 或 `ignored_video` 的条目；下载失败在配置的冷却期后重试；“验证更新”模式重新下载已知 URL 以发现同 URL 内容替换。一个分类同一时间只允许一个活动运行。

Raindrop 页面适配器按最新优先，在遇到整页均已知条目时停止；Workers API 适配器扫描稳定 ID。最大扫描页数为可选参数，留空表示扫描站点返回的全部页面。只有分类与脚本曾成功完成不限制页数的基线采集后，才允许使用“整页已知”提前停止；失败、中断或限制页数的运行不能建立基线，重跑时已下载的待审核来源跳过下载，但仍继续枚举后续页面。动态分页可能因采集期间新增内容而在相邻页面返回重复条目，因此适配器和运行服务都必须按稳定来源键执行运行内幂等去重；数据库写入失败后必须先回滚事务，再持久化运行失败状态，避免任务永久停留在运行中。替代方案是仅依赖 URL/文件名比较，无法处理内容更新和失败重试，因此不采用。

每个运行条目另外保存不可变的采集结果，后续拒绝或入库只更新业务状态，不覆盖采集结果。运行统计采用两层漏斗：扫描条目由旧来源跳过、下载成功、忽略、技术无效和失败组成；下载成功由新增审核候选、采集内容重复和图库重复组成。全局资产总览按互斥业务状态统计唯一 SHA256 资产，不能与网页条目数量混用。

### 审核只给客观提示，导入由人确认

服务计算尺寸、像素数、宽高比、模糊度和解码有效性。有效图片只显示低像素、极端比例、模糊等提示，不能自动拒绝；损坏、非图片或超限文件标记为技术无效并删除临时二进制。相似候选复用现有 DINO 与感知哈希能力，只在待审核采集资产之间分组，不读取正式图库。扫描由用户手动启动并持久化为可查询进度的任务；新结果完整生成后再替换旧结果，失败时保留上一次成功结果。

这样保留用户对题材和内容的最终判断，也避免采集分类与人物识别的双重真相。导入后仍执行现有图库识别流程，结果以图库侧为准。

### 使用快照关系支持历史导出

`AcquisitionImportedPhoto` 对每张成功入库图片保存运行、资产、`gallery_photo_id`（可空且 `ON DELETE SET NULL`）、图库 ID/文件名/SHA256/分类快照。图库删除后不恢复图片；导出清单会标注缺失项目而跳过不存在的对象。

选择快照而非持久复制原图，既保证可追溯，又不额外保存被删除图片。替代方案是为每次运行保留一套副本，会导致存储膨胀且违背图库删除语义。

入库历史的默认浏览入口按 `AcquisitionImportBatch` 分组。批次列表只显示时间、状态和数量摘要；选择批次后，再分页查询该批次的逐图结果。逐图结果通过资产标识动态聚合采集运行和来源，不在批次表中重复保存来源文本。同一资产关联多个运行时仍只显示一行，并在展开详情中列出全部来源。图库图片后来被删除时，界面使用溯源快照显示原图库标识并明确标注当前文件缺失。

旧版本可能已经写入成功溯源，但没有对应的成功入库批次。此类资产归入固定的“历史导入（未关联批次）”虚拟批次，继续支持分页查看，避免升级后历史记录从界面消失。批次筛选与导出范围使用各自独立的日期条件，防止浏览历史时无意改变导出范围。

“入库与导出”页面采用三个纵向全宽区域：入库批次、所选批次的入库溯源、创建导出与导出任务。批次和明细区域使用受限高度、内部滚动和服务端分页；导出表单与任务列表合并为紧凑区域且始终可见，任务列表高度受限。该布局避免逐图文件名无限拉长页面，也不把常用导出能力隐藏到弹窗或折叠面板中。

### ZIP 导出采用临时对象和流式生成

导出任务将每个正式 MinIO 对象逐个流式写入 `data/tmp/acquisition-exports` 下的 ZIP 文件，再上传至 `workspaces/{workspace_id}/acquisition/exports/{job_id}.zip` 临时对象并删除本地临时文件。浏览器下载由受权 API 流式转发，下载成功即删除对象；任务中断或未下载对象由 24 小时 TTL 清理。ZIP 还包含 `metadata.json`。

使用本地临时文件避免将大 ZIP 置于内存，MinIO 临时对象则使前端轮询、重试下载和清理可控。替代方案是实时边压缩边响应，无法为异步任务提供可靠状态和重试。

### 权限与运行期恢复沿用现有模式

成员可浏览和导出；`can_edit_gallery` 管理站点、分类和相似扫描；`can_add_gallery` 启动、重试和提升；`can_delete_gallery` 拒绝候选或删除临时资产。运行、条目与导出任务保留检查点；启动时将未完成运行标记为可恢复中断状态，并执行过期导出清理。第一版不引入队列或调度器。

启动恢复同时处理未完成导入批次和旧版遗留的 `importing` 资产。若同 SHA256 图库图片已经存在，则幂等补齐溯源并清理临时对象；否则转为“导入失败”等待用户重试。图库 SHA256 重复只作为淘汰结果保存，不写成功入库溯源。

## 风险与取舍

- [站点页面或 API 改版] → 适配器隔离、运行失败可见、保留来源 URL 与错误摘要，并允许逐站点更新适配器。
- [大批量图片占满本地内存或磁盘] → 下载和导出逐文件流式处理，下载大小上限可配置，导出临时文件完成即删除。
- [提升中进程中断造成双对象或不一致] → 使用确定性目标键、显式 `importing` 状态、重试时检查图库 SHA256 与对象存在性，确认后才删除临时对象。
- [DINO 扫描成本较高] → 不在每次下载后自动扫描，仅由用户手动发起并分页展示候选。
- [旧 `catchPics` 数据不完整] → 迁移命令先提供 dry-run，保持原目录只读，不根据缺少状态文件删除或覆盖原资源。

## 迁移计划

1. 新增配置字段、表和 MinIO 操作；启动时通过现有 SQLite 初始化机制创建表、补齐列，并把旧站点上的单一 `adapter_key` 迁移为脚本定义及站点绑定。
2. 部署内置 Raindrop 适配器、采集 API 与采集中心页面；旧采集脚本和资源目录保持可用。
3. 使用迁移命令先 dry-run 查看将导入的站点、分类、条目和文件，再显式执行迁移；迁移只复制至临时工作区并记录来源。
4. 启用新流程后，历史采集继续由旧目录保留；回滚时停止新 API/UI 使用即可，已入正式图库的图片按既有逻辑保留。

## 未决问题

- 第一版内置 `raindrop-ftxsri-workers-dev` 与 `shfwzwz-raindrop-page` 两个适配器；后续新增脚本的准入流程为代码评审和发布，暂不提供用户可编辑的解析规则或代码上传。
- 质量阈值先以配置默认值提供，后续根据实际审核结果再调整，不纳入自动拒绝策略。
