## 背景

当前后端约有 103 个接口集中在单个 `main.py` 中，该文件同时负责应用初始化、数据库兼容处理、服务实例化、认证与权限、对象转换、文件流、后台任务和业务路由。前端 `App.tsx` 超过 5000 行，包含约 128 个状态及认证、工作空间、图库、人物、上传、视频和字幕等多个领域；`api.ts` 与 `styles.css` 也承担了所有领域职责。

项目尚无自动化测试，且 MinIO、Qdrant、人脸模型、FFmpeg 和字幕服务具有较重的启动依赖。重构必须保持现有业务行为，同时遵守未经用户授权不得主动启动前后端程序的仓库约束。

## 目标与非目标

**目标：**

- 建立按业务领域划分的前后端模块边界，降低入口文件规模和跨领域耦合。
- 保持 API、数据库、界面、Hash 路由、本地存储和媒体处理行为兼容。
- 提供可注入测试配置和伪造外部服务的 FastAPI 应用工厂。
- 增加足以保护结构重构的 API 契约、权限和关键前端纯逻辑测试。
- 留下明确的后续重构清单，使后续会话可以直接继续推进。

**非目标：**

- 不修改业务需求、页面设计和用户操作流程。
- 不修改数据库表结构，不引入 Alembic，不迁移现有数据。
- 不重写人脸识别、图片导入、视频转码和字幕算法。
- 不引入 React Router、全局状态框架、Ruff、ESLint 或自动格式化工具。
- 不在实施过程中主动启动前端或后端开发服务器。

## 设计决策

### 1. 后端使用应用工厂和领域路由

新增 `create_app` 作为统一组装入口，生产环境继续导出模块级 `app`。配置、生命周期、服务容器、依赖和路由注册由应用工厂连接，各领域路由仅依赖明确的服务与数据库接口。

选择应用工厂而不是继续依赖模块级全局对象，是为了让测试能够跳过真实外部资源预热并注入临时数据库。不会引入完整依赖注入框架，避免为当前规模增加额外复杂度。

路由按认证与系统、工作空间、人物与标签、图库与任务、视频与字幕、统计分组。必须保持现有方法、路径和注册顺序，尤其保留静态路径优先级。

### 2. 权限改为路由显式声明

当前权限依赖通过请求方法和 URL 前缀推断权限，新增路由时容易遗漏或误判。重构后由修改类路由显式声明九项现有权限之一，认证上下文只负责用户和工作空间解析。

该调整不改变权限结果。实施前先建立现有权限矩阵测试，覆盖新增、修改、删除图库，新增、修改、删除样本，以及新增、修改、删除视频。

### 3. 路由层仅负责协议适配

模型到响应 Schema 的转换、Range 请求解析、MinIO 流式响应和导入后台任务处理移出路由文件。路由负责参数解析、权限依赖、调用领域服务和返回响应。

当前被路由调用的 `PictureService` 下划线方法将改为明确的公共方法，算法和事务边界保持不变。大型服务文件暂不进一步拆分，以控制第一阶段改动范围。

### 4. 前端使用应用壳和领域 controller

认证和当前工作空间由应用壳持有。图库、人物、上传、视频和字幕各自使用类型明确的 hook/controller 保存状态和操作，页面组件只消费相应 controller。

所有领域 hook 在应用壳中稳定调用，页面切换时不卸载其状态，从而保持现有筛选、选择、草稿和上传队列状态。不会使用无类型的通用 Context，也不会把所有状态合并为单一全局 reducer。

视频续传队列具有多字段状态转换，单独使用纯 reducer 和存储适配器，便于测试序列化、恢复、失败重试和文件重新关联。

### 5. API 和样式按领域拆分

前端请求层由共享客户端统一处理认证 token、工作空间 header、错误解析和媒体 URL，再由领域模块提供现有函数。通过统一出口继续暴露原有函数名，避免组件层接口变化。

全局 CSS 按基础、应用壳、各业务页面、弹窗和响应式规则拆分，并通过固定入口保持原有加载顺序。第一阶段不采用 CSS Modules，避免选择器作用域变化造成视觉回归。

### 6. 先建立契约基线再搬运代码

后端保存规范化 OpenAPI 基线和有序路由表，比较路径、方法、参数、请求体、响应和 Schema，忽略自动生成的操作标识等非行为字段。测试使用临时 SQLite 和伪造外部服务，不访问真实 MinIO、Qdrant、模型或 FFmpeg。

前端使用 Vitest 测试 Hash 路由、请求客户端、格式化工具和视频队列 reducer。页面视觉与完整操作流程继续通过构建检查和用户手动启动后的浏览器烟雾验证确认。

## 风险与权衡

- **风险：路由拆分改变匹配顺序或响应契约** → 在搬运前固化有序路由表和 OpenAPI 契约，按领域逐组迁移并持续比较。
- **风险：显式权限声明遗漏接口** → 建立九项权限矩阵，并检查每个非只读路由是否声明权限或明确属于认证、工作空间例外。
- **风险：前端拆分导致切页后状态重置** → controller 始终由应用壳调用，页面仅负责展示，不把需要持久保留的状态下沉到会卸载的组件。
- **风险：拆分 CSS 改变层叠顺序** → 只做文件搬运，保持规则原顺序和选择器文本，并进行构建及关键页面截图对比。
- **权衡：大型服务文件仍然偏大** → 第一阶段优先降低入口耦合，服务内部算法拆分留到独立后续变更，降低一次性回归范围。

## 迁移计划

1. 建立契约和关键逻辑测试，确认当前基线可重复运行。
2. 引入后端应用工厂和依赖注入入口，再逐领域迁移路由、转换器、媒体响应和后台任务。
3. 引入前端共享客户端、领域 controller 和顶层页面组件，再拆分 API 与 CSS。
4. 清理未使用文件，执行 Python 编译、后端测试、前端测试和生产构建。
5. 用户手动启动项目后完成认证、工作空间、图库、人物、上传、视频、字幕和统计烟雾验证。

每个阶段保持可构建和可测试；若出现无法定位的行为回归，按最近一个领域迁移提交回退，不回退已通过的基线测试和测试基础设施。
