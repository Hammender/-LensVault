结论先说：方向对，但不能按现在这份稿直接开工。 它把“线程爆炸”“重复解码/重复计算”“交互任务被后台拖死”三件事揉成一个大调度器，线程预算算错了，还有几处会引入新的卡
 死或灰屏。

 当前代码里，真正相关的现状是：

 - OpenCV 已经在首次质量分析时 cv2.setNumThreads(1)，而且只设一次。
 - 采集下载默认 8 路，下载和分析在同一个 worker 里做。
 - 人脸默认是 CPU ONNX（FACE_EXECUTION_PROVIDERS=CPUExecutionProvider），InsightFace 检测会话 没有 SessionOptions。
 - 采集阶段已经做了一次解码出质量和 pHash/dHash；相似扫描仍会重新下载、重算，并再跑一遍人脸。
 - NumPy / OpenBLAS / Torch 线程完全没限制。

 ────────────────────────────────────────────────────────────────────────────────

 1. 根因判断不完整

 方案默认：CPU 高是因为 OpenCV 内部线程失控，所以撤掉 setNumThreads(1)，改成「4 张图 × 每算子 4 线程」。

 这只覆盖了问题的一部分，而且可能是已经修过的那一部分。

 更可能的叠加是：

 ┌────────────────────┬───────────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────┐
 │ 来源               │ 现状                                                          │ 方案有没有管                                                            │
 ├────────────────────┼───────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
 │ OpenCV 内部线程    │ 已设成 1                                                      │ 要改回 4                                                                │
 ├────────────────────┼───────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
 │ ONNX 人脸检测      │ InsightFace 默认 intra_op ≈ 逻辑核数，且默认走 CPU            │ 只写了“检测和特征模型设 4/1”，但检测会话不在你们自己的 OnnxFaceAdapter  │
 │                    │                                                               │ 里                                                                      │
 ├────────────────────┼───────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
 │ NumPy/OpenBLAS/MKL │ assess_image_quality、_quality_image 大量 mean/percentile/var │ 完全没提                                                                │
 ├────────────────────┼───────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
 │ 采集并发           │ 8 个 worker 下载完立刻做 CPU 分析                             │ 只做许可，不拆流水线                                                    │
 ├────────────────────┼───────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
 │ 重复计算           │ 相似扫描无视已有 quality_version，每张再解码、再算、再跑人脸  │ 这部分是对的                                                            │
 ├────────────────────┼───────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
 │ Torch DINO         │ CUDA 回退 CPU 时会占满核                                      │ 没提                                                                    │
 └────────────────────┴───────────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────┘

 如果现在 CPU 高是在 已经 setNumThreads(1) 之后测到的，再把 OpenCV 调回 4 线程，大概率更热，不是更稳。

 人脸这条更关键：buffalo_l 检测器是 InsightFace 自己建的 InferenceSession，你们现在只给了 providers，没有线程配置。CPU 上 1 张图就能把 20 核打满；4 张并行会再叠
 一层。方案写“线程限制仅控制 CPU 推理”，但 检测模型是 CPU 占用的大头，却最不容易设进去。

 ────────────────────────────────────────────────────────────────────────────────

 2. 「16 逻辑线程预算」算错了

 并行图片数 × 库线程数 <= 16 只在「全世界共用一个线程池」时成立。实际上不是：

 - 4 个 OpenCV 池
 - 4 个 ONNX intra 池
 - 4 个 OpenBLAS 池
 - 外层还有采集 8 worker、图库识别 4 worker、FastAPI 默认线程池

 最坏是 4×4 + 4×4 + 4×N，不是 16。
 ONNX 4 线程和 OpenCV 4 线程也不会合并。

 另外，1600px / 1024px 上的 Sobel、Gaussian、Laplacian、ORB，内部 4 线程收益很小，上下文切换成本倒不小。对这类图，更稳的是：

 图级并行 2～4，库线程 1。
 而不是撤掉 setNumThreads(1)。

 成功标准也有问题：「重任务时 CPU 70%–90%」测的是饱和度，不是浪费。用户要的是「这点活不该把机器打满」。应分开看：

 - 轻负载（1 张图）：线程数接近 1，CPU 不该打满
 - 重负载：吞吐、单图耗时、线程总数有上界
 - 线程数不随图片数线性爆炸

 ────────────────────────────────────────────────────────────────────────────────

 3. 调度器设计有几个硬坑

 统一入口、有界并行、异常必须释放许可，这些是对的。下面几条按现在写法会出事。

 ### 3.1 下载和分析还在同一条线程上

 方案说「下载不占计算名额」，但采集仍是 _download_and_analyze()：同一个 ThreadPoolExecutor 线程先下载，再申请许可，再分析。

 结果是：8 个下载线程里，4 个在算，4 个在等许可，没人继续下下一张。下载并发会被计算许可拖死。
 要名实相符，必须拆成下载队列和计算队列，下载线程分析前把活交出去。

 ### 3.2 许可和 single-flight 顺序没定义

 两种顺序都有坑：

 - 先拿许可再进 single-flight：等待者白白占着名额
 - 先进 single-flight 再拿许可：才是对的

 稿子没写。并发相同 key 时，既可能重复算，也可能 4 个名额被等待者占满。

 ### 3.3 嵌套许可会死锁

 「内部函数不能重复申请」只能靠线程局部标记。一旦持有许可的代码又丢进另一个线程（采集已有 executor，图库识别也有），子线程看不到标记，会再申请 → 死锁。

 必须写死：持有许可期间禁止再 submit 到别的池并同步等待。 这比“内部别重复申请”更硬。

 ### 3.4 缩略图不该进这个池

 缩略图是请求路径，主要是解码 + JPEG。
 「不抢占」意味着一张大人脸 CPU 推理几秒内，缩略图只能排队。这会直接变成列表灰屏——而方案的手工验收标准恰好是「列表刷新不长时间灰屏」。

 交互优先的正确做法是：缩略图走自己的短超时、小并发，不要和采集/相似/人脸抢同一个 4 槽。最多设一个独立的轻量上限。

 ### 3.5 15 秒老化会把后台抬成交互级

 相似扫描等 15 秒升一级，30 秒就和缩略图、入库同级。长时间扫描时，反饥饿会重新压住交互。
 老化可以留，但不要升到最高档；或者给交互留保留槽（例如 4 槽里固定 1 个给请求路径）。

 ### 3.6 人脸运行时线程安全没写

 FaceService 是进程单例。图库导入已经用 2 个 worker 并发打同一个 InsightFace 对象。方案提到 4，没有锁，也没有会话池。InsightFace 的 FaceAnalysis.get() 对并发并不
 稳。要么串行人脸，要么多实例，要么加锁。不能只靠「最多 4 张图」。

 ────────────────────────────────────────────────────────────────────────────────

 4. 哪些是对的，应该留

 这些值得做，而且不依赖那个大调度器：

 1. 启动时设一次线程，之后不许改。 OpenCV 文档说 setNumThreads 非线程安全，现在放在依赖检查里是懒加载，人脸 warmup 可能已经先用过 OpenCV。应在
    initialize_runtime()、人脸 warmup 之前设完。
 2. 单次解码上下文。 采集已有 _analyze_image_payload()，但质量、哈希、人脸、元数据仍会各解一次。图库导入是 parse_image_metadata + detect_faces（内部再解成 BGR）
    。这是实打实的浪费。
 3. 相似扫描复用库里已有特征。 scan_similarity() 现在几乎无视已有 quality_version，每张都重算，还跑人脸。这比线程数更能解释「这点压力不该这么高」。
 4. 主脸质量和完整识别不能混用。 现有 primary_face_* 只是优势脸质量，不是多脸识别结果。这条写得很对。
 5. 计算期间不要握着 SQLite 写事务。 相似扫描一边算一边 db.add，许可一等待就可能锁整库。这和灰屏、database is locked 是对得上的。
 6. 采集转图库时拷贝已验证哈希/质量。 避免入库再算一遍。
 7. 失败不进 single-flight 缓存、取消要释放许可。 原则对。

 DecodedImageContext 要注意内存：一张 6000×4000 的 RGB+BGR+灰+镜像，大约几十到上百 MB；4 路并行就上 GB。上下文必须短命，镜像/BGR 按需生成，用完丢掉。

 ────────────────────────────────────────────────────────────────────────────────

 5. 方案过重，建议拆开

 现在这稿是一个独立性能大改，但里面至少有四层，风险和收益差很多：

 ┌──────────────────────────────────────────────────┬────────────────────────────┬──────┬────────┐
 │ 层                                               │ 收益                       │ 风险 │ 建议   │
 ├──────────────────────────────────────────────────┼────────────────────────────┼──────┼────────┤
 │ 进程级库线程封顶（OpenCV/ONNX/OpenBLAS/Torch）   │ 直接打中线程爆炸           │ 低   │ 先做   │
 ├──────────────────────────────────────────────────┼────────────────────────────┼──────┼────────┤
 │ 停止重复解码、重复算、扫描复用 DB                │ 直接打中“这点活不该这么重” │ 中   │ 先做   │
 ├──────────────────────────────────────────────────┼────────────────────────────┼──────┼────────┤
 │ 采集下载和分析拆队列，CPU 有界                   │ 中高                       │ 中   │ 第二批 │
 ├──────────────────────────────────────────────────┼────────────────────────────┼──────┼────────┤
 │ 全局优先级调度器 + 老化 + single-flight + health │ 锦上添花                   │ 高   │ 先不要 │
 └──────────────────────────────────────────────────┴────────────────────────────┴──────┴────────┘

 采集热路径上，每张图 SHA 都是新的，single-flight 几乎没用。它只对「扫描 + 入库同时打同一张图」有意义，不该成为主设计。

 GALLERY_RECOGNITION_WORKERS=4 也没必要先改。最终仍受 4 个许可限制，只是多种了等待线程。保持 2，先把库线程和复用做对。

 ────────────────────────────────────────────────────────────────────────────────

 6. 还漏了的实现点

 1. InsightFace 检测器怎么设 intra_op_num_threads。 现有 OnnxFaceAdapter 只包了识别模型。检测器在 FaceAnalysis(...) 里，不改这里，ONNX 限制就是空话。可能要包装
    detector session，或用环境变量在 import 前钉死。
 2. 进程级 OMP_NUM_THREADS / MKL_NUM_THREADS / OPENBLAS_NUM_THREADS / torch.set_num_threads。 不设的话，OpenCV=4 也管不住 NumPy。
 3. OCR。 图文导入会走 RapidOCR，同样是 ONNX，不在调度器里。
 4. 人脸 CUDA 时的 CPU 预处理。 即使用 GPU，InsightFace 仍有 OpenCV 预处理；线程限制不能只写在 CPU provider 分支。
 5. 配置要同步 .env。 按仓库规则，新字段必须进本地 .env 和 .env.example，运行时只读 .env。
 6. 健康接口加字段。 只加只读键一般兼容，但要确认没有客户端做严格 schema 校验。
 7. 视频采集。 方案只覆盖图，没问题，但不要把视频探测/转码也塞进图像许可。

 ────────────────────────────────────────────────────────────────────────────────

 7. 若仍要做调度器，最小修正

 1. 不要撤 setNumThreads(1)，除非压测证明单图 OpenCV 是瓶颈。默认建议 MAX_PARALLEL=2～4，LIBRARY_THREADS=1。
 2. 启动时统一设置 OpenCV / ORT / OpenBLAS / Torch，之后禁止改。
 3. 必须能改到 InsightFace 检测会话，不只是识别适配器。
 4. 先 single-flight，再拿许可；持有许可时不准再同步等别的池。
 5. 下载池和计算池分开。
 6. 缩略图独立，不进这 4 个槽。
 7. 老化不要升到最高优先级；给交互留保留槽。
 8. 人脸推理加锁或实例池。
 9. 成功标准改成：线程上界、单图耗时、轻负载 CPU、重复计算次数，而不是“CPU 70%–90%”。

 ────────────────────────────────────────────────────────────────────────────────

 一句话： 重复计算和库线程失控是真问题；全局优先级协调器是过度设计，线程公式是错的，缩略图进同一池会把灰屏做回来。先做「启动封顶所有原生线程 + 单次解码 + 扫描走
 DB 缓存 + 计算时放开 SQLite 写锁」，这四项就能解释并压住大部分异常 CPU。调度器放到有数据之后再说。
