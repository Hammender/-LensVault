## 手工启动

MinIO 和 Qdrant 容器已恢复并通过连接检查。日后容器停止时，从项目根目录启动现有容器：

```powershell
docker start pictureshow-minio pictureshow-qdrant
```

在第一个终端启动后端：

```powershell
cd E:\code\PictureShow
conda activate pictureshow
python -m uvicorn app.main:app --app-dir backend
```

在第二个终端启动前端：

```powershell
cd E:\code\PictureShow\frontend
cmd /c npm.cmd run dev
```

## 后续拉取与开发

共享文件由 Git 管理，本机运行数据由各设备独立维护：

| 文件 | 管理方式 |
| --- | --- |
| `alembic.ini` | 提交公共迁移路径和日志配置，不保存本机连接串或凭据 |
| `backend/alembic/env.py`、`script.py.mako`、`versions/*.py` | 全部提交；迁移脚本与对应模型改动一起交付 |
| ORM 模型、`sql/tables.sql`、迁移生成工具、依赖清单 | 同步提交与迁移相关的变化 |
| `.env.example` | 提交字段及非敏感示例默认值 |
| `.env`、SQLite 数据库、`alembic_version` 表、`data/` 备份、缓存 | 各设备独立保存，不提交 |

根目录 `alembic.ini` 的旧忽略规则已解除，且此文件已与当前四个有效迁移脚本一起纳入 Git；其他设备拉取后可获得同一份公共迁移配置。归档的旧脚本不再提交。

拉取前先停止前后端。保留本机 `.env`，不要用其他电脑的配置覆盖它。在项目根目录先核对迁移版本：

```powershell
conda activate pictureshow
python -m alembic heads
python -m alembic current
```

`heads` 应只显示一个最新版本，且没有重复 revision 警告。`current` 已与 head 一致时无需升级；存在待执行迁移时，确认脚本已完成审查，再执行：

```powershell
python -m alembic upgrade head
python -m alembic check
```

升级后 `current` 应与 head 一致。若出现未跟踪的旧迁移脚本或数据库引用未知 revision，先核对历史，不要通过改版本号或 `stamp head` 跳过实际升级。

拉取、只读检查和常规迁移不自动创建全库备份；备份仅在用户明确要求时执行。常规表结构变更以逐行审查迁移脚本为主，不要求每次额外建库演练，也不要求各设备重复验证已审查的迁移。只有审查无法确认数据保留、回填结果或兼容性时，才用少量构造数据做针对性隔离验证。临时数据库及相关产物放在系统临时目录，正常结束和异常退出均关闭连接并自动清理，不留在仓库或 `data/` 下。涉及大表操作时按实际操作评估锁持有时间和额外空间，涉及可能丢失数据的操作时先说明影响并取得用户明确授权。

新增或修改模型结构后，按根目录 `AGENTS.md` 生成并审核迁移脚本、同步 `sql/tables.sql`，将迁移脚本与模型一起纳入 Git。`generate_migration` 工具用于生成草稿的临时空库已有自动清理机制。实际迁移是 `backend/alembic/versions/` 下的 Python 脚本，`sql/tables.sql` 是生成的全量表设计文件。迁移脚本通过 Git 同步，数据库内容和本机模型文件仍属于本地运行数据。

两台设备从同一个 revision 各自新增迁移时，合并代码后可能出现多个 head。应保留双方脚本，审核操作是否冲突，再新增 merge revision 汇合迁移链；存在具体疑点时补充针对性验证。不能删除另一台设备已执行的脚本或直接改写其前驱，也不能用 `stamp head` 跳过真实结构变更。分支合并机制见 [Alembic 官方迁移分支说明](https://alembic.sqlalchemy.org/en/latest/branches.html)。同一人轮流使用不同设备时，先拉取并按本机版本决定是否升级，再生成新迁移，通常可以保持单一迁移链。
