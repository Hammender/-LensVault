## 手工启动

MinIO 和 Qdrant 容器已恢复并通过连接检查。日后容器停止时，从项目根目录启动现有容器：

```powershell
docker start pictureshow-minio pictureshow-qdrant
```

在第一个终端启动后端：

```powershell
cd E:\code\PictureShow
conda activate pictureshow
python -m uvicorn app.main:app --app-dir backend
```

```powershell
cd E:\code\PictureShow\frontend
```

## 后续拉取与开发

共享文件由 Git 管理，本机运行数据由各设备独立维护：

| 文件 | 管理方式 |
| --- | --- |
| `alembic.ini` | 提交公共迁移路径和日志配置，不保存本机连接串或凭据 |
| `backend/alembic/env.py`、`script.py.mako`、`versions/*.py` | 全部提交；迁移脚本与对应模型改动一起交付 |
| ORM 模型、`sql/tables.sql`、迁移生成工具、依赖清单 | 同步提交与迁移相关的变化 |
| `.env.example` | 提交字段及非敏感示例默认值 |
| `.env`、SQLite 数据库、`alembic_version` 表、`data/` 备份、缓存 | 各设备独立保存，不提交 |

本次发现根目录 `alembic.ini` 仍被旧忽略规则排除，已解除该规则；此文件当前为未跟踪状态，需要与本轮修正一起由用户提交，之后其他设备才能通过拉取获得同一份配置。当前四个有效迁移脚本已经被仓库跟踪，归档的旧脚本不再提交。

拉取前先停止前后端。保留本机 `.env`，不要用其他电脑的配置覆盖它。SQLite 处于 WAL 模式时应使用 SQLite 备份接口创建一致性快照，再在项目根目录执行：

```powershell
conda activate pictureshow
python -m alembic heads
python -m alembic current
python -m alembic upgrade head
python -m alembic check
```

`heads` 应只显示一个最新版本，且没有重复 revision 警告；`current` 在升级后应与该版本一致。若出现未跟踪的旧迁移脚本或数据库引用未知 revision，先核对历史，不要通过改版本号或 `stamp head` 跳过实际升级。

新增或修改模型结构后，按根目录 `AGENTS.md` 生成并审核迁移脚本、同步 `sql/tables.sql`，将迁移脚本与模型一起纳入 Git。迁移脚本通过 Git 同步，数据库内容和本机模型文件仍属于本地运行数据。

两台设备从同一个 revision 各自新增迁移时，合并代码后可能出现多个 head。应保留双方脚本，审核操作是否冲突，再新增 merge revision 汇合迁移链，并在临时数据库验证后提交。不能删除另一台设备已执行的脚本或直接改写其前驱，也不能用 `stamp head` 跳过真实结构变更。分支合并机制见 [Alembic 官方迁移分支说明](https://alembic.sqlalchemy.org/en/latest/branches.html)。同一人轮流使用不同设备时，先拉取并升级本机数据库，再生成新迁移，通常可以保持单一迁移链。
